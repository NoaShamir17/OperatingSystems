i have a question about realloc when size < old_size, why wouldnt it sucseed freeing memory? when would we need to allocate a new block for this case and why?

Based on the assignment instructions, here is the explanation for why shrinking a memory block (size < old_size) might not succeed in-place, and why a new allocation is required in that specific case.

1. Why wouldn't it succeed in freeing memory in-place?
The system cannot always just "chop off" the end of a block to free it. To free the excess memory (the difference between old_size and size), the allocator must be able to turn that remainder into a new, independent "free block" and add it to the linked list.

This process ("splitting") will fail if the remainder is too small.


Metadata Overhead: Every block in your linked list usually requires a "header" or metadata to track information like its size and the pointer to the next block. If the leftover space is smaller than the size of this metadata, you cannot create a valid block structure there.


Alignment Constraints: The assignment requires all memory allocations to be multiples of 4 bytes. If the split would result in a block that violates this alignment or leaves a "sliver" of memory too small to be useful (e.g., 1 or 2 bytes), the split is rejected.

2. When would we need to allocate a new block?
According to the assignment logic, you must allocate a completely new block when the split is impossible.

The instructions state that if the function "does not succeed in freeing the blocks in the suitable way" (i.e., it cannot split the block due to the size constraints mentioned above), it must trigger the fallback mechanism:

Allocate a new block of the requested size.

Copy the data from the old block to the new one (truncated to size).

Free the entire old block.

3. Why allocate a new block instead of keeping the old one?
It might seem inefficient to move data just to shrink it, but there is a logic to this requirement regarding fragmentation:

Reclaiming the Large Block: If you kept the original large block but only used a small part of it (because you couldn't split it), that wasted space is "trapped" inside the allocation (Internal Fragmentation). By moving the data to a new, smaller block that fits it tightly (Best Fit), you can free the entire original large block.

Future Use: That original large block is now available in the free list to satisfy a future request for a large allocation, rather than being tied up holding a small amount of data.

whar is %zu printf type

%zu is the format specifier used in printf specifically for variables of type size_t.

Why do we need it?

size_t is an unsigned integer type, but its size changes depending on your system architecture:

On 32-bit systems: size_t is usually 4 bytes (like unsigned int).

On 64-bit systems: size_t is usually 8 bytes (like unsigned long).

If you try to print a size_t using %u (for unsigned int) or %lu (for unsigned long), your code becomes non-portable:

Using %u on a 64-bit system might truncate the value (printing garbage for large numbers).

Using %lu on a 32-bit system might expect more bytes than provided, leading to stack corruption or wrong output.

%zu solves this by telling printf: "I am providing a size_t; please adjust yourself to whatever size that happens to be on this machine."

Example
C
size_t mySize = sizeof(int);
printf("Size of int: %zu bytes\n", mySize);

Note: Since your assignment flags include -std=c99, using %zu is perfectly standard and correct.

Under normal, bug-free execution, it is impossible for a valid allocated block's end address to be strictly greater than the Program Break (PB).

The Program Break is, by definition, the "end of the valid heap world." Nothing exists beyond it.

However, we include checks like ptr >= sbrk(0) or worry about this scenario for three specific reasons:

1. Catching User Errors (Sanity Check)
The check in your customFree and customRealloc:

C
if((size_t)ptr >= (size_t)sbrk(0)) { ... }
This is not there because we might place a block there. It is there because the user might pass a garbage pointer.

Example: A user tries to free a variable allocated on the Stack. Stack addresses are usually much higher than Heap addresses (often exceeding sbrk(0)).

Example: A user tries to free a pointer that they already freed, and since then, the heap has shrunk (via brk). That old pointer now points to "unmapped memory" above the new PB.

2. Heap Corruption (Buffer Overflow)
This is a common disaster scenario.

Imagine you have Block A. The user writes past the end of Block A's payload.

They overwrite the header of Block B, changing its size from 100 to 1,000,000.

Now, when you calculate endOfBlock(B), the math says it ends way past sbrk(0).

If your logic detects this (e.g., end > sbrk(0)), it's a sign that the heap metadata has been corrupted by a buffer overflow.

3. The "Exact Match" vs. "Greater Than"
Valid: endOfBlock(block) == sbrk(0)

This is perfectly fine. It means this is the last block in the heap. It fills the space exactly up to the limit.

Invalid: endOfBlock(block) > sbrk(0)

This implies the block claims to own memory that the OS hasn't given us. This is always a bug or corruption.

Summary
In your logic, endOfBlock being bigger than PB is impossible if the heap is healthy. The checks exist solely to defend your allocator against bad users passing invalid pointers or corrupted memory states.

The definition of calloc(n, size) is that it allocates a contiguous array of n objects. In C, arrays are packed tightly. There is no "padding" inserted between elements by the allocator.

If you aligned before multiplying: ALIGN(3) = 4.

Total: 
2×4=8
 bytes.

To check for multithreading errors (like race conditions and deadlocks), you cannot use the standard Memcheck tool. You need to switch Valgrind's "tool" entirely.

The industry-standard tool for this is Helgrind.

The Command
Bash
valgrind --tool=helgrind --history-level=full ./main
Breakdown of Flags
--tool=helgrind: Switches Valgrind from the default memory checker to the thread error detector.

--history-level=full: (Highly Recommended) When a race condition is found, this flag ensures Valgrind prints the full stack trace of both conflicting threads (the one reading and the one writing). Without this, you only see "conflicting access" but not who caused it.

What Helgrind Detects
Data Races: Two threads accessing the same memory location without a lock (and at least one is writing).

Example: Thread A reads counter while Thread B increments counter.

Lock Order Violations (Potential Deadlocks): Thread A locks M1 then M2, while Thread B locks M2 then M1.

API Misuse: Unlocking a mutex you don't own, destroying a locked mutex, etc.

Alternative Tool: DRD
If Helgrind is too slow or reports too many errors, you can try DRD. It is lighter but sometimes misses edge cases.

Bash

what other tools might be relevant for MT or memory managment?

Beyond Valgrind (Helgrind/DRD), there are three other powerful categories of tools that are standard for debugging multithreading and memory management in C.

1. The Compiler Sanitizers (The "Modern Standard")
Modern GCC and Clang compilers have built-in "Sanitizers". These are often faster and more accurate than Valgrind because they instrument the code at compile time rather than running it in a virtual machine.

A. ThreadSanitizer (TSan) This is arguably the best tool for Part B of your assignment. It detects data races (accessing memory without a lock) and deadlocks.

How to use: Add -fsanitize=thread to your compile flags.

Bash
gcc -g -pthread -fsanitize=thread -std=c99 customAllocator.c tests.c -o tests
Run: Just run the executable normally: ./tests

Why use it? It gives extremely readable error reports showing exactly which two lines of code raced against each other.

Note: You cannot use TSan and Valgrind at the same time.

B. AddressSanitizer (ASan) Great for detecting out-of-bounds accesses and use-after-free errors.

How to use: -fsanitize=address

Limitation: Like Valgrind, ASan mostly tracks standard malloc. However, it is excellent for checking if your test code (the user of the allocator) is behaving correctly.

2. GDB (The "Surgeon")
When your threaded program hangs (deadlock) or crashes (segfault), GDB is the only way to inspect the "frozen" state.

Key Multithreading Commands:

info threads: Lists all currently running threads and where they are stuck.

thread apply all bt: Prints a "Back Trace" for every thread. This is the #1 way to spot a deadlock (e.g., Thread 1 waiting for Mutex A, Thread 2 waiting for Mutex B).

set scheduler-locking on: Forces GDB to run only the current thread while pausing others. This allows you to step through one thread's logic without another thread interfering.

3. Strace (The "Spy")
Since your assignment relies on sbrk and brk (system calls), strace is invaluable. It prints every system call your program makes to the kernel.

How to use:

Bash
strace ./main
Or filter only for memory calls:

Bash
strace -e trace=brk,sbrk,mmap,munmap ./main
Why use it?

It proves definitively whether your allocator is actually asking the OS for memory or if it's just recycling internal blocks.

If you see brk(0x...) = 0x... followed by exit_group(1), you know exactly when and why your program crashed or exited.

Development: Use ThreadSanitizer (-fsanitize=thread) while coding Part B. It catches races instantly.

Debugging Hangs: Use GDB (info threads) if the program freezes.

Verification: Use Strace to ensure your sbrk calls match your expectations.

The reason you see no error is that standard C runtimes are "passive." They do not strictly police whether you clean up every single object before you quit or free memory.

Here is the breakdown of why this happens and what mutex_init actually does under the hood.

1. What does pthread_mutex_init actually do?
When you call pthread_mutex_init(&myMutex, NULL), you are essentially telling the system: "Please set up the memory at this address to act as a lock."

It does two main things:

Sets Internal Variables: It writes specific values into the pthread_mutex_t struct (which resides in your heap or static memory). It sets flags like "unlocked", "no owner", and "default protocol".

Prepares for Kernel Interaction (Futex): On Linux, mutexes use a mechanism called a Futex (Fast Userspace Mutex). Most of the work happens in user-space memory (checking if the variable is 0 or 1). The kernel is only involved if there is contention (waiting).

Crucially: pthread_mutex_init usually does not allocate new heap memory itself. It just initializes the data structure you provided.

2. Why brk(heapStart) "hides" the crime
When you call brk(heapStart), you are telling the Operating System: "I am done with all this memory. You can take it back."

The OS moves the Program Break pointer back to the start.

The memory where your mutexes lived is now effectively "unmapped" or marked as invalid for your process.

The "mutex" concept vanishes because the physical bytes that represented it are gone.

The system does not scan that memory before freeing it to say, "Hey, wait! There is an active mutex at address 0x1234!" It just blindly reclaims the pages. Since the memory is gone, the mutex is gone. If no other thread tries to touch it after the brk, no error occurs.

3. Is this bad?
Technically, yes, it is bad practice, even if it doesn't crash.

Resource Leaks: While simple mutexes on Linux are mostly just memory, some advanced mutex types (or on other OSes) might allocate internal kernel resources (handles) that need explicit destruction. If you just free the memory without calling destroy, those kernel handles might leak (until the process terminates).

Undefined Behavior: The POSIX standard says that freeing the memory underlying a mutex without destroying it first is Undefined Behavior.

Debug Tools: If you run this with Valgrind or Helgrind, they will scream at you. They track every initialized mutex and will report "Mutex destruction missing" or similar errors.

what does pthread mutex destroy does

pthread_mutex_destroy is the cleanup function for a mutex. Think of it as the "shutdown procedure" for that specific lock.

Here is exactly what it does, and why it might seem like it "does nothing" in simple cases.

1. It Invalidates the Object
The primary job of destroy is to mark the mutex object as invalid.

It often writes a specific "garbage" value into the mutex structure.

If you try to lock or unlock this mutex after destroying it, the program will crash or return an error (instead of deadlocking or behaving unpredictably). This is a safety mechanism.

2. It Checks for "Busy" Errors
This is its most useful feature for debugging.

If you try to destroy a mutex that is currently locked (by any thread), pthread_mutex_destroy will fail and return EBUSY.

This warns you that your logic is flawed: "Hey, you are trying to delete this lock, but someone is still using it!"

3. It Releases Kernel Resources (Sometimes)
On Linux (Default): A standard mutex is often just a simple counter in user-space memory. In this case, destroy doesn't strictly need to talk to the kernel, so it feels like it does nothing.

On Other Systems / Special Mutexes: If you use "recursive" or "error-checking" mutexes, or if you are on an OS closer to Windows, the mutex might have a hidden handle or a pointer to a kernel object. pthread_mutex_destroy is responsible for telling the kernel: "We are done with this handle, you can free it." If you skip this, you leak kernel resources.

Why brk(heapStart) made it irrelevant for you
In your specific case, your mutexes live inside your Header structs, which live in the heap.

You called brk(heapStart), effectively telling the OS "I don't need this memory anymore."

The OS reclaimed the pages.

Since the process was ending (or the heap was being reset), the OS cleans up all kernel resources associated with the process anyway. You didn't see an error because you bypassed the safety check (destroy) and just deleted the universe the mutex lived in.
